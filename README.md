Part 1 — Hands-on Technical Inspection & Automation

Scenario A — Offline Sync & Data Collision

Risk model

A device-local ID such as `School_1` is not globally unique. If Ankit and Pooja both generate `School_1`, the server must never use `localId` alone as its primary identity.

I would use:

text
serverSurveyId = UUID generated by server
clientRecordKey = deviceId + ":" + localId
idempotencyKey  = clientRecordKey + ":" + surveyVersion


Example:

text
ankit-phone:School_1
pooja-phone:School_1


These are different records even though their local IDs are equal.

For repeated retries from the *same* device, the same idempotency key must return the original server record instead of creating another copy.

### API contract used by the mock

POST /sync-survey`

json
{
  "deviceId": "ankit-phone",
  "localId": "School_1",
  "surveyVersion": 1,
  "capturedAt": "2026-10-22T10:00:00Z",
  "answers": {
    "schoolName": "Govt Primary School"
  }
}


Expected behavior:

| Case | Expected |
|---|---|
| First `(deviceId, localId)` | `201 Created` |
| Same request repeated | `200 OK`, same `serverSurveyId`, no duplicate |
| Same `localId`, different device | `201 Created`, different server ID |
| Same device/local ID but changed immutable identity | `409 Conflict` or explicit version/update response; never silent overwrite |
| Missing required identity fields | `400 Bad Request` |
| Two identical requests concurrently | Exactly one persisted record |

### Scaling / DDoS protection

50,000 workers reconnecting at once is a thundering-herd problem. I would combine:

1. **Client-side jitter** — do not sync every device immediately at connectivity restoration.
2. **WorkManager constraints** — network-connected constraint plus retry/backoff.
3. **Exponential backoff with jitter** — especially for 429/5xx.
4. **Server idempotency** — safe retries without duplicate writes.
5. **Batch sync** — upload bounded batches instead of thousands of requests per device.
6. **Rate limiting / admission control** — protect API and database.
7. **Queue-based ingestion** — API acknowledges durable receipt and an asynchronous worker handles heavy processing where appropriate.
8. **Connection pooling and DB indexes** on the idempotency key.
9. **Observability** — request rate, 429/5xx, queue depth, sync latency and duplicate rate.

I would load-test a reconnect storm using k6/JMeter/Gatling, gradually increasing concurrency rather than jumping directly to 50,000.

### Poor-network photo upload: 99% failure

I would test a matrix of:

- upload fails before bytes are sent
- fails around 50%
- fails around 99%
- TCP reset after server receives the request
- app killed immediately after failure
- network changes Wi-Fi -> mobile -> offline
- duplicate retry after partial upload
- device reboot before retry
- storage becomes full during retry

**Charles/Proxyman:** throttle bandwidth and latency, then abort/reset the connection near the end of the request. Where exact byte-level interruption is not available, use a controlled mock endpoint that intentionally closes the connection after a known threshold.

**ADB:**

```bash
adb shell svc wifi disable
adb shell svc data disable
adb shell svc wifi enable
adb shell dumpsys connectivity
adb logcat -c
adb logcat | grep -i -E "sync|workmanager|okhttp|retrofit|upload|error"
```

Acceptance criteria:

- local survey remains present after failure
- upload state becomes retryable, not permanently failed
- no duplicate server record after retry
- photo is either atomically accepted or safely re-uploaded
- WorkManager retry/backoff is observable
- user-facing state clearly indicates pending sync

# Scenario C — Room & WorkManager

The Android specification says surveys must be fillable and saved completely offline, with local storage such as Room, and background sync when connectivity returns using WorkManager. fileciteturn1file3L266-L271

## Inspect Room data on an unrooted test device

The exact feasibility depends on the APK's build type and whether the app exposes a debug/test export path. I would **not** claim that a normal production APK allows arbitrary access to `/data/data/<package>/databases/`.

### Preferred QA approach

For a QA/debuggable build:

```bash
adb shell run-as com.example.app ls -la databases
adb shell run-as com.example.app ls -la databases/
adb shell run-as com.example.app \
  "cp databases/app.db /sdcard/app.db"
adb pull /sdcard/app.db
sqlite3 app.db ".tables"
sqlite3 app.db "SELECT * FROM survey;"
```

If `run-as` fails on a release/non-debuggable APK, I would request one of:

- internal debuggable build
- QA-only database export
- test-only diagnostic endpoint
- Android Studio Database Inspector against an allowed debug build

I would never root a production field device simply to inspect data.

### Before-sync verification

1. Clear app state.
2. Disable connectivity.
3. Create a survey.
4. Save/exit.
5. Force-kill/reopen app.
6. Verify answers are still present.
7. Inspect the Room row using the approved debug mechanism.
8. Record local ID, sync state, retry count and timestamps.
9. Re-enable connectivity.
10. Trigger sync.
11. Verify server receipt.
12. Re-check local row and confirm the state transitioned only after successful server acknowledgement.

### WorkManager execution

I would first identify the WorkManager worker and its constraints through logs/test instrumentation. A production APK does not expose a universal ADB command that safely "runs any WorkManager job immediately"; that depends on the app's worker implementation.

For a QA build, I would add a debug-only trigger:

```text
adb shell am broadcast \
  -a com.example.app.DEBUG_RUN_SYNC
```

or an exported debug activity/deep link that calls the same application sync scheduler.

For diagnosis:

```bash
adb shell dumpsys jobscheduler
adb logcat | grep -i WorkManager
```

The key QA principle is to invoke the same production scheduling path, not create a test-only fake sync path.

### 500 retry test

1. Put device and proxy on the same network.
2. Install the proxy CA on the QA device.
3. Route the app through Charles/Proxyman.
4. Match `POST /sync-survey`.
5. Return HTTP 500.
6. Start sync.
7. Confirm request is visible.
8. Confirm local Room record remains.
9. Inspect WorkManager logs/state.
10. Restore 200 response.
11. Wait for or trigger retry.
12. Confirm exactly one server record exists.
13. Confirm local state changes to synced only after success.

Expected state machine:

```text
LOCAL_SAVED
    |
    v
SYNC_PENDING
    |
    +---- 5xx/network failure ---> SYNC_PENDING + retry scheduled
    |
    +---- 2xx -------------------> SYNCED
```

### Profiling

Use Android Studio Profiler / Perfetto to compare:

- Java/Kotlin heap
- native heap
- bitmap allocations
- retained Activities/Fragments
- video buffers
- disk I/O
- CPU
- frame rendering

The strongest root-cause evidence would be a reproducible memory curve:

```text
Module 1 -> 180 MB
Module 2 -> 260 MB
Module 3 -> 370 MB
Module 4 -> 510 MB
```

followed by GC pressure, allocation failure, severe frame stalls or ANR.

If memory does **not** grow, investigate:

- main-thread disk I/O
- synchronous database work
- video decode contention
- repeated layout inflation
- blocking network calls
- lock contention

### Low-storage simulation

Prefer a dedicated emulator/test device or QA device reset rather than damaging a field phone.


Exact available storage should be measured before and after; the goal is to reproduce thresholds, not guess them.

# Scenario E — HFC Engine Test Plan

The builder supports HFC actions `flag_silently`, `reask_once`, `reask_and_flag`, and `block`; `match=all` means AND and `match=any` means OR. fileciteturn2file3L168-L200

| ID | Scenario | Input | Expected |
|---|---|---|---|
| HFC-01 | Positive AND | age=14, education=College | `reask_and_flag` |
| HFC-02 | Positive OR | either condition true | fires |
| HFC-03 | Negative | age=20, education=College | no action |
| HFC-04 | Boundary | age=15 | does not fire for `< 15` |
| HFC-05 | Boundary | sleep=6 | does not fire for `< 6` |
| HFC-06 | Missing value | one referenced field empty | defined non-match; no crash |
| HFC-07 | Type mismatch | `"15"` vs `15` | deterministic coercion policy |
| HFC-08 | `reask_once` first match | invalid value | prompt appears |
| HFC-09 | `reask_once` second same value | invalid again | accept + flag; no loop |
| HFC-10 | corrected after reask | first invalid, second valid | continue, no infinite loop |
| HFC-11 | `block` | invalid value | cannot proceed until corrected |
| HFC-12 | `flag_silently` | invalid | no prompt; flag stored |
| HFC-13 | `show_sup=1` | rule fires | supervisor can see flag |
| HFC-14 | Multiple rules | two rules fire | deterministic ordering |
| HFC-15 | Unknown attribute | invalid schema | schema validation fails before deployment |
| HFC-16 | Duplicate rule ID | duplicate ID | schema validation rejects |
| HFC-17 | Roster scope | one member invalid | flag belongs to correct roster row |
| HFC-18 | Offline | no network | HFC still executes on-device |
| HFC-19 | App restart after reask | state persisted | no accidental second infinite cycle |
| HFC-20 | Very large schema | many rules | bounded execution time |

### Important defect found in the supplied sample schema

The supplied JSON contains an HFC with:

```json
"questioID": "q_2"
"questioID": "q_3"
```

and the two objects are missing a comma between them. Therefore the file, as supplied, is not valid JSON. fileciteturn2file4L290-L302

There is also a logic contradiction: `q_3` is visible when `q_2 = No`, while the HFC shown for `q_3` checks `q_2 = Yes`. fileciteturn2file4L282-L309

I would raise these as release-blocking schema defects rather than silently modifying the supplied attachment.

Automate when the test is:

- repeatable
- deterministic
- business-critical
- regression-prone
- data-driven

Keep manual when it requires:

- visual judgement

# Part 4 — UI/UX & User-Centric QA

The target is not a generic smartphone user. The supplied app specification explicitly calls for budget phones, low connectivity, limited reading skills, visual-heavy training, large touch targets and visual feedback. fileciteturn1file3L257-L264

For the proposed Training Video Hub with a standard video player, three text-heavy paragraphs and a standard-sized Next button, I would flag:

| Risk | Why it matters | Test |
|---|---|---|
| Too much text | Low-literacy users may not understand the workflow | Observe task completion with minimal reading |
| Small/standard touch target | Budget-device users may miss it | Tap accuracy test; verify touch target dimensions |
| Next button only at bottom | Forces scrolling and may be hard to discover | Test one-handed use and long content |
| Poor sunlight contrast | Outdoor field use can make controls unreadable | Test outdoors / high brightness |
| Color-only feedback | Users may not distinguish status by color alone | Use icon + text + color |
| Video buffering / storage pressure | Offline training must work on low storage | Repeat 3–4 modules on 4 GB device |
| Tiny video controls | Difficult on small screens | Test portrait mode and touch accuracy |
| Orientation/layout issues | Small screens can clip content | Portrait/landscape and font scaling |
| Missing progress state | User may not know whether training is complete | Kill/reopen and verify state |
| Accessibility | Visual-only UI excludes some users | TalkBack, font scaling, contrast |

### Systematic approach

I would test at minimum:

- representative 4 GB RAM Android device
- smallest supported screen
- portrait orientation
- 100% and increased font scale
- bright outdoor/high-brightness condition
- low storage
- offline mode
- slow 2G-like network for any content that must download
- TalkBack
- repeated navigation/process death

### Bug communication

Use a defect format that separates **observation** from **impact**:

```text
Title:
Training Hub - Next button is only reachable after long scroll

Environment:
Android X / 4 GB RAM / portrait / build 1.2.3

Steps:
1. Open Training Video Hub
2. Start module
3. Return to screen
4. Attempt to continue

Actual:
Next button is below three dense paragraphs and is not visible without scrolling.

Expected:
Primary continuation action is easy to discover and reachable with minimal scrolling.

User impact:
High. Field worker with limited literacy may not understand that more content is below the fold.

Evidence:
Screenshot/video + device details.

Recommendation:
Keep the primary action sticky or place a clearly discoverable CTA after the essential visual content.
```

The goal is constructive: explain the user impact, provide evidence, and offer a practical direction without dictating the final design.

## How to present this in an interview

I would emphasize three principles:

1. **Data safety first** — local data must survive every network failure.
2. **Schema safety before UI regression** — validate the generated contract before testing every dynamic screen.
3. **Risk-based automation** — automate deterministic regression; use human exploration where judgment is the test.
